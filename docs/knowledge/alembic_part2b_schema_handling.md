## Handling PostgreSQL Schemas in Alembic

Audime uses 4 PostgreSQL schemas. In `env.py` we configured:

- `include_schemas=True` — makes Alembic reflect all schemas, not just the default one
- `include_name` — filters only `None` (default), `raw`, `core`, `staging`, `analytics`

Each model declares its schema via `__table_args__`:

```python
class Usuario(Base):
    __tablename__ = "usuario"
    __table_args__ = {"schema": "core"}
```

Autogenerate will generate operations like:

```python
op.create_table(
    "usuario",
    sa.Column("id_usuario", sa.BigInteger(), ...),
    schema="core",
)
op.create_table(
    "nota",
    sa.Column("id_nota", sa.BigInteger(), ...),
    schema="raw",
)
```

## Handling SQLite in Tests

SQLite **does not support named schemas**. The `conftest.py` already handles this using `schema_translate_map`:

```python
execution_options={
    "schema_translate_map": {"raw": None, "core": None, "staging": None, "analytics": None}
}
```

In Alembic's `env.py`, we do the same when `ALEMBIC_DB_DRIVER=sqlite`. SQLite also **does not support** `ALTER COLUMN`, `DROP COLUMN`, or `ALTER TABLE` for many operations. Alembic works around this with `op.batch_alter_table()`.

> ⚠️ **Important:** if a migration uses `batch_alter_table`, the code generated by autogenerate may need manual adaptation for SQLite. Always test migrations in SQLite as well.
