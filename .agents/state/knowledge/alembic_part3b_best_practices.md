# Alembic Part 3b: Best Practices, Pitfalls, and Conclusion

*Continuation of `alembic_part3_operations.md` — operational guidance.*

---

## Best Practices and Common Pitfalls

### Do

1. **Always review migrations generated by autogenerate** — it does not understand intent (rename vs drop+add)
2. **Always write the `downgrade()`** — even if complex, it is essential for safe rollback
3. **Use `nullable=True` when adding columns to existing tables** — then backfill and `alter_column(nullable=False)` in a separate migration
4. **Commit migrations to Git together with model changes** — so they are always in sync
5. **Test migrations in staging before production**
6. **Keep migrations small and focused** — one change per migration
7. **Include `alembic check` in CI** — to detect models changed without a corresponding migration

### Don't

1. **Do not edit migrations already applied to production** — create a new migration
2. **Do not rely 100% on autogenerate** for renaming columns/tables
3. **Do not add `NOT NULL` columns without a default to tables with data** — it will break
4. **Do not mix schema migration with data migration in the same revision** (use separate or use `-x data=true`)
5. **Do not ignore "multiple heads" errors** — merge with `alembic merge`

### Common Pitfalls

| Problem | Cause | Solution |
|---------|-------|----------|
| "Multiple heads detected" | Two devs created migrations with the same `down_revision` | `alembic merge -m "merge" <rev1> <rev2>` |
| "Can't locate revision" | Migration removed or `down_revision` points to nonexistent revision | Restore the migration or fix the chain |
| Column drop lost data | Autogenerate saw a rename as drop+add | Always review: replace with `alter_column(..., new_column_name=...)` |
| Enum not detected | Autogenerate does not handle ENUMs well | Use `alembic-postgresql-enum` or declare manually |
| Migration stalls on large table | DDL without considering existing data | Do it in multiple steps: add nullable → backfill → add NOT NULL |

### Merge of Branches

When two migration branches diverge:

```bash
alembic heads
alembic merge -m "merge feature-x" abc123 def456
alembic upgrade head
```

### Data Migrations vs Schema Migrations

For data migrations (backfill, data transformation), use the Cookbook pattern with `-x`:

```bash
alembic -x data=true upgrade head
```

And in `script.py.mako`, include conditional logic to separate schema_upgrades from data_upgrades.

## Conclusion for Audime

Alembic is **highly recommended** for Audime. Replacing `scripts.sql` with versioned migrations brings:

1. **Traceability**: every schema change has a commit, author, date, and message
2. **Safety**: downgrade allows reverting problematic changes
3. **Automation**: autogenerate reduces manual errors and accelerates development
4. **Test integration**: SQLite in tests with `schema_translate_map` works perfectly
5. **Collaboration**: migrations are versioned code in Git — no more "run this SQL on the database"

The transition is smooth: **stamp** the existing database, and from then on use `alembic revision --autogenerate` for all changes. Keep `scripts.sql` as historical documentation, but the source of truth becomes migrations.

### Summary Commands for Setup

```bash
# 1. Install
pip install alembic

# 2. Initialize
alembic init alembic

# 3. Configure env.py (content above)

# 4. Create empty baseline migration
alembic revision -m "initial_schema_baseline"

# 5. Stamp the current database
alembic stamp head

# 6. Test: create a dummy change and generate a migration
alembic revision --autogenerate -m "test_autogenerate"

# 7. Review what was generated, then revert
alembic upgrade head
alembic downgrade -1
```
