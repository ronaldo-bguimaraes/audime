## Technical decisions

### Stamp approach for initial migration
Empty migration (upgrade/downgrade = pass) because the schema already exists via `scripts.sql`. `Base.metadata` is the source of truth. Avoids duplicating already-applied DDL.

### 4-level URL precedence
More refined implementation than the spec (3 levels):
1. `sqlalchemy.url` from config (if != placeholder) — for testing
2. `ALEMBIC_DB_URL` env var — explicit override
3. Project `Settings` — PostgreSQL production
4. `sqlite:///./test.db` — dev fallback

### config.attributes["connection"] for tests
env.py accepts external connection via `config.attributes`, enabling testing with in-memory SQLite. Standard pattern recommended by official documentation.

### version_table_schema per environment
- PostgreSQL: `"core"` — alembic_version table in core schema
- SQLite: `None` — SQLite does not support schemas

### include_schemas disabled on SQLite
When `is_sqlite=True`, `include_schemas=False`. The `schema_translate_map` already maps schemas to None.

### include_name callback
Filters schemas: raw, core, staging, analytics, None. Essential to avoid polluting system schemas (pg_catalog etc).

### scripts.sql preserved
Diff detected is from a previous commit (5edb20f — UNIQUE constraint). CAT-015 is a false positive in this cycle.

## Lessons learned

### Stamp approach and alembic check
`alembic check` returns exit code 1 when there are differences between database and models — even with intentional stamp. This is not an error, it is expected behavior. **Lesson:** Document that `alembic check` will fail until the first real migration. If CI depends on exit code 0, consider a baseline migration with `create_all` instead of stamp. [MEMORY]

### URL precedence and testing
The spec had 3 levels of precedence; the implementation added a 4th (config file URL) because tests need to set the URL programmatically via `set_main_option`. Without this, in-memory SQLite tests would not work. **Lesson:** Always test URL precedence logic with programmatic config overrides. [EXECUTION]

### config.attributes["connection"] and the Alembic test pattern
Using `config.attributes["connection"]` is the only reliable way to test migrations with in-memory SQLite. Without it, each Alembic command would create a new connection — and in-memory databases are ephemeral per connection. **Lesson:** This pattern should be copied to all projects that test Alembic with SQLite. [EXECUTION]

### Multi-schema in Alembic requires include_schemas + include_name
For projects with PostgreSQL schemas beyond public, it is mandatory:
1. `include_schemas=True` — Alembic only sees the default schema without this
2. `include_name` callback — filters system schemas
3. `schema_translate_map` on SQLite — maps schemas to None
**Lesson:** Multi-schema configuration is the most critical and least documented part of Alembic setup. Test on both PostgreSQL and SQLite. [CONSTRAINT]

### SQLite in Alembic: limitations and workarounds
SQLite does not support schemas, ALTER COLUMN, DROP COLUMN, nor several PostgreSQL types (JSONB, BIGINT without with_variant). Alembic works around this with `batch_alter_table()` and `schema_translate_map`. **Lesson:** Never use `--autogenerate` against SQLite — always generate migrations against PostgreSQL. SQLite is for testing only. [CONSTRAINT]

### False positives in diff validation
CAT-015 failed because `git diff HEAD -- scripts.sql` was not empty, but the modification was from a previous commit. **Lesson:** Validation of "file not modified" should compare the cycle's commit diff, not diff against HEAD, to avoid false positives when the file was modified in previous cycles and committed together. [EXECUTION]
